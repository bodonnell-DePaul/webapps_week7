Real-Time Web Communication, MCP & PWAs

Web Development — Week 8

Polling · HTTP Streaming · SSE · WebSockets · SignalR · WebRTC · MCP · MCP Apps · PWA

~3-hour lecture.

1. Why "real-time" matters

  • The web started as a pull medium. Modern users expect push.
  • Chat, AI typing, dashboards, video, multiplayer — all the same question:
  • Who pushes data? When? Over which wire?
  • There is no "best" tech — only the right shape for the problem.

2. Pick the communication model first

  • Direction — S→C, C→S, both, peer↔peer?
  • Latency budget — ms, sec, "eventually"?
  • Fan-out — 1:1, 1:many, many:many?
  • Reliability — must every message arrive in order?
  • Lifecycle — short request, persistent, or background?

Decide the model before you reach for an API.

3. HTTP Baseline

  • Stateless, client-initiated, request → response.
  • Half-duplex per request.
  • Friendly to CDNs, caches, proxies.
  • Every real-time tech either bends, replaces, or bypasses HTTP.

HTTP — when it's still right

  • CRUD, REST, GraphQL queries/mutations.
  • User-initiated reads / form submits.
  • Latency budgets measured in seconds, not milliseconds.

Real world: GitHub REST API

  • The product. GitHub's REST API at api.github.com: each call is an independent HTTPS request that returns JSON.
  • Conditional requests. Most endpoints return an ETag; resend it as If-None-Match and unchanged data answers 304 Not Modified.
  • Why it fits. A 304 to a correctly authorized request does not count against the primary rate limit.
  • Rate limits. 60 requests/hour unauthenticated, 5,000/hour for authenticated users; after 403/429 wait for x-ratelimit-reset.
  • Trade-off. Still pull-only: GitHub says to subscribe to webhook events instead of polling the API.

Source: docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api · docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api

4. HTTP Polling

Short polling: ask every N seconds

Client ──GET /updates──► Server (every 5s)
Client ──GET /updates──► Server

+ Trivial, stateless, universal.

– Wasted requests; latency = poll interval.

4. Long Polling

Client ──GET /updates──► Server (holds…)
                          ↓ data arrives
Client ◄────payload───── Server
Client ──GET /updates──► Server (immediately reconnects)

+ Near real-time, HTTP-friendly, survives proxies.

– Many idle open sockets; one message per round-trip.

Polling — use cases

  • "Is my batch job done?" status checks.
  • Low-frequency dashboards (≥ 30s tick).
  • Hostile-network fallback (still hidden inside SignalR).

Real world: GitHub Events & Notifications API

  • The product. GET /events and GET /notifications on api.github.com, both documented as "optimized for polling".
  • Server sets the pace. X-Poll-Interval: 60 means poll at most every 60 s; the value can grow under load, so obey it.
  • Cheap empty polls. Send If-None-Match (events) or If-Modified-Since (notifications); nothing new → 304, rate limit untouched.
  • Trade-off. Latency ≥ the poll interval; public events can lag 30 s to 6 h ("not built to serve real-time use cases").

Source: docs.github.com/en/rest/activity/events · docs.github.com/en/rest/activity/notifications

Real world: Telegram Bot API

  • The product. Bots call getUpdates on api.telegram.org to "receive incoming updates using long polling".
  • How it holds. timeout (seconds) keeps the request open until an update arrives; 0 is short polling, for testing only.
  • Acknowledge. The next call sends offset = last update_id + 1, which confirms earlier updates; they are kept at most 24 hours.
  • Also seen in. Socket.IO starts with HTTP long-polling, then upgrades; SignalR falls back to it after WebSockets and SSE.

Source: core.telegram.org/bots/api#getupdates · socket.io/docs/v4/how-it-works · learn.microsoft.com/aspnet/core/signalr/introduction

5. HTTP Streaming

One long response, body delivered in chunks.

Client ──POST /chat──► Server
        ◄──chunk 1── (token 1)
        ◄──chunk 2── (token 2)
        ◄──chunk 3── (token 3)
        ◄──────────  end

This is how ChatGPT-style "typing" UIs work.

HTTP Streaming — capabilities

+ Client can POST and stream back.

+ Binary-safe, no new protocol.

+ Works with auth headers, middleware, CDN.

– No automatic reconnect (you write it).

– No standard framing — agree on a format (NDJSON, etc.).

– One-way, like SSE.

Real world: Kubernetes API watch

  • The product. GET /api/v1/namespaces/test/pods?watch=1 streams Pod changes from the API server.
  • How it streams. 200 OK, Transfer-Encoding: chunked; the body is a stream of JSON events like {"type":"ADDED","object":{…}}.
  • Resume. Every object has a resourceVersion; after a disconnect, start a new watch from the last one you saw.
  • Watch for. History is short (etcd 3: 5 minutes by default); an expired version returns 410 Gone — list again, then re-watch.

Source: kubernetes.io/docs/reference/using-api/api-concepts/ (efficient detection of changes)

6. Server-Sent Events (SSE)

Standardized server→client streaming over HTTP. text/event-stream + browser EventSource.

Client ──GET /stream──► Server
       ◄── data: {…}
       ◄── event: update
           data: {…}
       (one persistent response, browser auto-reconnects)

SSE — pros

  • Simplest persistent server→client channel.
  • Built-in reconnection & Last-Event-ID resume.
  • Plays with every HTTP intermediary.
  • Ideal for LLM token streaming, dashboards, feeds.

SSE — cons

  • One-way only. Send back? Make a separate request.
  • Text/UTF-8 only.
  • EventSource cannot send custom headers (no Authorization) — use cookies, short-lived tokens, or fetch-event-source.
  • Long-lived sockets cost memory and file descriptors.

SSE — use cases

  • AI/LLM token streaming.
  • Stock tickers, sensor data, build pipelines.
  • Live sports/election feeds, news, comments.
  • Log tailing in DevOps dashboards.

Real world: Wikimedia EventStreams

  • The product. stream.wikimedia.org/v2/stream/recentchange serves live wiki edits as text/event-stream over plain chunked HTTP.
  • Resume. Each event id encodes the Kafka position, so a reconnecting EventSource sends Last-Event-ID and resumes.
  • Watch for. One-way; filtering is client-side. Connections end after 15 minutes, so the client must reconnect.
  • Also SSE. LLM APIs: set stream: true and the Anthropic Messages API sends tokens as server-sent events.

Source: wikitech.wikimedia.org/wiki/Event_Platform/EventStreams_HTTP_Service · platform.claude.com/docs/en/build-with-claude/streaming

7. WebSockets

RFC 6455 — upgrade HTTP → persistent, full-duplex TCP channel.

Client                       Server
  ──── GET /ws  Upgrade ────►
  ◄── 101 Switching Protocols ──
  ═══ framed text/binary  ═══►
  ◄═══ framed text/binary  ═══

WebSockets — capabilities

  • True bidirectional, low-latency messaging.
  • Text or binary payloads, optional per-message compression.
  • Subprotocols (graphql-ws, mqtt, custom).
  • Browser-native everywhere.

WebSockets — pros vs cons

Pros

  • Lowest-overhead bidirectional channel.
  • Symmetrical: either side can speak.
  • Predictable latency.
  • Ecosystem in every language.

Cons

  • You own the lifecycle.
  • Sticky sessions + backplane to scale.
  • Proxy hostility — need pings.
  • No HTTP semantics after upgrade.

WebSockets — use cases

  • Chat & collaboration (Slack, Teams, Discord).
  • Real-time collaborative editing (Google Docs, Figma).
  • Multiplayer games & low-latency state sync.
  • Trading dashboards & live auctions.
  • IoT control plane (often via MQTT subprotocol).

Real world: Discord Gateway

  • The product. One persistent WebSocket (wss://gateway.discord.gg) pushes events to bots and apps.
  • You own the lifecycle. Hello (heartbeat_interval) → Heartbeats → Identify (token, intents) → Ready (session_id).
  • Detect dead links. Each Heartbeat gets an ACK (opcode 11); no ACK means a "zombied" connection: close, reconnect, Resume.
  • Resume. Send session_id + last sequence number (opcode 6); missed events are replayed in order.
  • Limits. Identify is capped at 1,000 per 24 hours across all shards; Resume calls do not count.

Source: docs.discord.com/developers/events/gateway

8. SignalR

Microsoft's high-level real-time library for ASP.NET Core.

Negotiates transport (WS → SSE → Long Polling) behind a Hub programming model.

SignalR — what you get for free

  • Bidirectional RPC-style method calls.
  • Transparent transport fallback.
  • Groups, users, connection targeting.
  • Automatic reconnection.
  • ASP.NET Core auth integration.
  • Managed scale-out (Azure SignalR Service).

SignalR — pros vs cons

Pros

  • Huge productivity win on .NET.
  • Group targeting without a registry.
  • Built-in fallback + reconnection.
  • Clean cloud upgrade path.

Cons

  • Framework lock-in.
  • JSON default — switch to MessagePack at scale.
  • Silent long-polling fallback hides bugs.
  • Negotiation endpoint is a hotspot.

SignalR — use cases

  • Enterprise chat / collaboration on .NET.
  • Live ops/finance/support dashboards.
  • In-app real-time notifications.
  • Auctions, ticketing, order flow.
  • AI token streaming to .NET clients.
  • Signaling channel for WebRTC (next!).

Real world: Blazor Server and Azure SignalR Service

  • The product. Blazor Server runs C# UI components on the server, inside an ASP.NET Core app.
  • How it uses SignalR. UI updates, events and JS calls go over SignalR (WebSockets); the server keeps one "circuit" per browser screen.
  • Scale-out. Microsoft recommends Azure SignalR Service for Blazor Server apps to scale to many concurrent connections.
  • Trade-off. Every user interaction is a network hop: higher latency, and no offline support.

Source: learn.microsoft.com/aspnet/core/blazor/hosting-models · learn.microsoft.com/azure/azure-signalr/signalr-overview

9. WebRTC

Peer-to-peer, low-latency audio, video, and data — directly between browsers.

Browser A ◄── Signaling Server ──► Browser B
              (SDP, ICE via WS / SignalR)
       │                                  │
       └──── Direct P2P (SRTP/DTLS) ──────┘

WebRTC — pillars

  • MediaStream — mic, camera, screen capture.
  • RTCPeerConnection — codecs, NAT, encryption, transport.
  • RTCDataChannel — arbitrary data (text, JSON, binary).
  • Signaling — your responsibility (WebSockets/SignalR).

WebRTC — infrastructure

  • STUN — discover public IP behind NAT.
  • TURN — relay when peers can't connect (10–25% of sessions). Plan for it.
  • SFU — forward streams beyond ~4–6 peers.
  • MCU — mix/transcode for very large rooms.

"Works on my LAN with just STUN" is a trap. Always test TURN.

WebRTC — pros vs cons

Pros

  • Sub-100ms latency A/V.
  • P2P saves bandwidth + reduces latency.
  • Mandatory encryption.
  • Massive ecosystem.

Cons

  • Substantial complexity.
  • STUN/TURN/SFU infrastructure.
  • Mesh breaks past 4–6 peers.
  • Hard to observe server-side.

WebRTC — use cases

  • Video calling (Meet, Teams, Jitsi, Whereby).
  • Telehealth & telemedicine.
  • Customer support video + screen share.
  • Browser-native multiplayer games (data channels).
  • P2P file transfer & E2E-encrypted chat.
  • Live AI avatars / sub-second agents.

Real world: Jitsi Meet

  • The product. Open-source, browser-based video meetings (try it at meet.jit.si).
  • Two people. With exactly 2 participants it tries a direct P2P link (p2p.enabled); a 3rd person moves the call to the bridge.
  • Larger calls. Jitsi Videobridge, "a WebRTC-compatible Selective Forwarding Unit (SFU)", routes media between participants.
  • Signaling is separate. Prosody (XMPP) carries signaling; Jicofo manages media sessions and load-balances across videobridges.

Source: github.com/jitsi/jitsi-meet (README, config.js) · github.com/jitsi/jitsi-videobridge · jitsi.github.io/handbook/docs/architecture/

10. Service Workers

A JavaScript file the browser runs in its own background thread — a programmable network proxy between your app and the network.

  • No DOM access — separate global.
  • Lifecycle events: install / activate / fetch / push / sync.
  • Foundation for offline, push, install-to-home-screen.

Service Workers — caching strategies

StrategyBehaviorBest for
Cache-firstTry cache → networkStatic assets
Network-firstTry network → cacheFresh API data
Stale-while-revalidateServe cache, refresh bgAvatars, feeds
Cache-onlyCache, never networkTruly immutable
Network-onlySkip SWAuth, payments

Service Workers — pros & pitfalls

Pros

  • Foundation for offline / push / install.
  • Massive perf wins on repeat visits.
  • Language-agnostic backend.

Pitfalls

  • Cache invalidation is hard.
  • Lifecycle confuses everyone.
  • Buggy SW locks users into old version — keep a "kill switch".
  • HTTPS required (localhost ok in dev).

Real world: Squoosh and Excalidraw

  • Squoosh. Hand-written worker: install precaches into a versioned cache, activate deletes old caches, fetch is cache-first.
  • Squoosh updates. A message handler accepts skip-waiting, so the page can activate a new worker.
  • Excalidraw. README: "PWA support (works offline)". The worker is generated by vite-plugin-pwa (Workbox), registerType: "autoUpdate".
  • Caching rules. Fonts, locales and chunks are not precached; runtime rules use CacheFirst (fonts.css: StaleWhileRevalidate).

Source: github.com/GoogleChromeLabs/squoosh (src/sw) · github.com/excalidraw/excalidraw (README, excalidraw-app/vite.config.mts)

11. Web Push

Deliver a notification to the user even when the tab is closed. A doorbell, not a data channel.

Server ──VAPID-signed──► Push Service (FCM / Mozilla / Apple)
                                  │
                                  ▼
                       Service Worker `push` event
                                  │
                                  ▼
                       showNotification() → user

Web Push — pros vs cons

Pros

  • Re-engages without an app store.
  • Uses vendor push infra (no pipeline of your own).
  • Strong opt-in / revocable.

Cons

  • Permission friction.
  • iOS needs installed PWA (since 16.4).
  • Not real-time data — best-effort, ~4KB.
  • Easy to abuse → users mute you.

Web Push — use cases

  • Chat / mention notifications while user is away.
  • Calendar / meeting reminders.
  • Order, shipping, ride-share status.
  • Time-sensitive alerts (price drops, breaking news).

Real world: Mastodon Web Push

  • The product. Mastodon "natively supports the Web Push API" for alerts such as mentions, favourites, reblogs and follows.
  • Subscribe. POST /api/v1/push/subscription (user token, push scope) with the browser's endpoint, p256dh and auth keys.
  • Standards. subscription[standard]=true selects RFC 8030 + 8291 + 8292 (VAPID); the response returns server_key.
  • Watch for. One subscription per access token (a new one replaces the old); no direct Android/Apple gateways, use a proxy.

Source: docs.joinmastodon.org/methods/push/ · docs.joinmastodon.org/entities/WebPushSubscription/

12. Progressive Web Apps

A pattern, not a single technology:

  • Web App Manifest — name, icons, theme.
  • Service Worker — proxy, cache, push.
  • HTTPS — non-negotiable.
  • Responsive UI, install prompt, offline, push, background sync.

PWA — pros vs cons

Pros

  • Zero install friction.
  • One codebase, all platforms.
  • Auto updates.
  • Cheap MVP path.

Cons

  • iOS lags on some APIs.
  • Storage quotas can be reclaimed.
  • SW lifecycle is a learning curve.
  • Discoverability outside web.

PWA — examples in the wild

  • Twitter Lite, Pinterest, Starbucks, Uber.
  • News & media (offline-on-the-train).
  • Field-service & logistics in poor connectivity.
  • Internal tools that bypass the store.
  • Note-taking, time-tracking, productivity apps.

Real world: Twitter Lite

  • The product. A PWA that "became the default mobile web experience for all users globally in April 2017".
  • PWA parts. Service worker added in stages (offline page → static assets → app shell), Add to Home Screen, web push.
  • Reported results. 65% more pages per session, 75% more Tweets sent, 20% lower bounce rate.
  • Footprint. 600 KB over the wire vs 23.5 MB to install the Android app; returning visits boot in under 3 s.
  • Watch for. These are Twitter's own figures from the web.dev case study, not an independent benchmark.

Source: web.dev/case-studies/twitter

13. Do not use

  • HTTP/2 Server Push — Chrome removed support in 2022. Use HTTP streaming, SSE, or <link rel="preload"> instead.

If AI-generated code reaches for it, replace.

Real world: adjacent technologies

  • gRPC streaming — etcd: Watch is a bidirectional gRPC stream of key changes.
  • MQTT — AWS IoT Core: MQTT 3.1.1 and 5, QoS, retained messages.
  • GraphQL subscriptions — Hasura: results pushed over WebSocket (graphql-ws or subscriptions-transport-ws).

14. Decision tree

  • Anything real-time? No → REST. Stop.
  • Server → client only?
    • Low freq → polling.
    • High freq / stream → SSE (or HTTP streaming for auth POST).
  • Both directions?
    • .NET shop / productivity → SignalR.
    • Else → WebSockets.
  • Audio / video / sub-100ms? → WebRTC + WS/SignalR signaling.
  • Tab closed engagement? → Web Push + Service Worker.
  • Installable + offline? → PWA on top of any of the above.

15. Cross-cutting concerns

  • Scaling — sticky sessions, backplanes, region locality, backpressure.
  • Security — TLS, JWT validated on connect and per call, rate limits, input size caps.
  • Observability — connection counts, p95 latency, reconnect rate, fanout factor, transport mix.
  • Cost — egress dominates; idle connections aren't free; managed services trade $ for time.

16. Model Context Protocol (MCP)

  • An open protocol connecting AI hosts to external tools and context.
  • Host owns the user experience; an MCP client connects to MCP servers.
  • JSON-RPC: each request carries protocol version/client capabilities in _meta; server/discover advertises server versions/capabilities.
  • MCP standardizes integration — it is not a model, agent framework, or real-time event bus.

MCP server capabilities

Tools

  • Callable operations with names, descriptions, input schemas, handlers.
  • Example: lookup_order(order_id).

Resources

  • Addressable context the client can read: documents, reports, state.

Prompts

  • Reusable templates for common user tasks.

Transport

  • stdio for a locally launched server.
  • Streamable HTTP for a remote server.
  • Use an SDK; keep stdio stdout reserved for protocol messages.

Implementing an MCP tool

  1. Choose a user task; expose the smallest useful operation.
  2. Define a precise input schema and a clear description.
  3. Call existing services; validate and authorize on the server.
  4. Return bounded, structured results; make writes explicit and idempotent.
  5. Test discovery, invalid input, authorization, failures, cancellation.
lookup_order({ order_id })
  → validate + authorize
  → orderService.lookup(order_id)
  → { status, updated_at, items }

Tool descriptions/results are an API contract. Host approval does not replace server authorization.

Real world: GitHub MCP Server

  • The product. github/github-mcp-server "connects AI tools directly to GitHub's platform" (repos, issues, PRs, workflows).
  • Remote (Streamable HTTP). Hosted by GitHub at https://api.githubcopilot.com/mcp/; sign in with OAuth or a personal access token.
  • Local (stdio). Run the Docker image ghcr.io/github/github-mcp-server with GITHUB_PERSONAL_ACCESS_TOKEN set.
  • Narrow the tools. Remote URLs select toolsets (/mcp/x/actions, /mcp/x/all); a /readonly suffix limits to read-only tools.
  • Watch for. GitHub Enterprise Server does not support remote server hosting, so use the local server there.

Source: github.com/github/github-mcp-server (README.md, docs/remote-server.md)

17. MCP Apps: tool + UI resource

  • A tool can link to an interactive HTML view using ui:// resource metadata.
  • A capable host fetches the resource and renders it in a sandboxed iframe.
  • The Apps SDK handles initialization and the view ↔ host JSON-RPC bridge.
  • Views request tool calls through the host; the host mediates access and results.
  • Keep a useful normal tool result for hosts that do not support Apps.

MCP Apps — safe implementation

  • Build a focused HTML view; register it as a UI resource and associate it with a tool.
  • Wait for host initialization; use the supported SDK bridge for actions and results.
  • Use least-privilege sandbox/CSP origins and permissions.
  • Never put API keys or privileged credentials in the view or tool result.
  • Re-check authorization in every server-side handler; handle loading, errors, and accessible fallback.

The iframe is not a trust boundary for business rules; host support is optional.

Real world: MCP Apps in Claude and VS Code

  • Examples. The ext-apps repo has a CesiumJS globe, a PDF viewer and a system monitor; its README demo is Excalidraw in Claude.
  • Hosts. The community-kept client matrix lists Claude, ChatGPT, VS Code GitHub Copilot, Goose, Postman and others.
  • In VS Code. Support was announced on 26 Jan 2026; Storybook's MCP server renders component previews in chat.
  • Watch for. Support varies by host (VS Code labels it experimental); keep a text result for hosts without the view.

Source: github.com/modelcontextprotocol/ext-apps · modelcontextprotocol.io/extensions/client-matrix · code.visualstudio.com/blogs/2026/01/26/mcp-apps-support · code.visualstudio.com/docs/agent-customization/mcp-servers

18. MCP + real-time: different jobs

  • MCP — command/context plane: discover tools, start an action, read a resource.
  • Real-time channel — event plane: deliver ongoing progress, collaboration, or media.
  • A tool call can create a job and return a job_id.
  • SSE / SignalR / WebSockets deliver authorized updates; MCP remains the action interface.
User → host → MCP: start_export → job_id
Export job → SSE / SignalR → browser or MCP App

Choose the channel for the event flow

  • SSE: one-way progress and status; reconnect with event IDs.
  • WebSockets / SignalR: bidirectional collaboration and frequent updates.
  • WebRTC: peer audio/video or peer data; signaling is separate.
  • Web Push: background doorbell, not the live progress stream.
  • MCP transport streaming is not automatically a durable, multi-viewer app subscription.

Integration checklist

  • Correlate MCP calls, job IDs, and events; job IDs outlive request IDs.
  • Authorize job creation, status reads, subscriptions, and cancellation.
  • Handle ordering, duplicate events, reconnect/resume, retention, terminal status.
  • Keep status as a source of truth; support timeouts, cancellation, backpressure.
  • Keep credentials and sensitive payloads out of UI resources and event logs.

MCP invokes the action; the real-time channel delivers the ongoing experience.

Real world: MCP over HTTP

  • Streamable HTTP. Each client message is an HTTP POST; the reply is JSON or a text/event-stream (SSE) stream.
  • Progress. A progressToken in _meta makes the server stream notifications/progress on that response.
  • Live changes. subscriptions/listen holds a stream open for list_changed and resources/updated notifications.
  • Long jobs. Tasks extension: the server returns a task; the client polls tasks/get; task IDs survive disconnects.
  • Revision note. 2026-07-28 has no initialize, Mcp-Session-Id or SSE resume; after a broken stream, re-send the request.

Source: modelcontextprotocol.io/specification/2026-07-28 · modelcontextprotocol.io/extensions/tasks/overview. Spec revision checked: 2026-07-28.

19. Recap (one paragraph)

Plain HTTP pulls. Polling fakes push by asking on a loop. HTTP streaming delivers one long response in chunks (today's LLM token UX). SSE standardizes that for server→client with auto-reconnect. WebSockets turn HTTP into a bidirectional pipe. SignalR wraps WS/SSE/long-polling in a productive .NET abstraction. WebRTC opens encrypted P2P media and data between browsers. Service workers are the programmable network proxy that powers offline and background. Web Push rings the user's doorbell when the tab is closed. PWAs package it all into installable, offline-capable apps. MCP standardizes how AI hosts discover and invoke tools; MCP Apps add an optional interactive view. Pair MCP commands with SSE, SignalR, WebSockets, or WebRTC when users need ongoing updates or peer media.
